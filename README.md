# Сканер ягід (прототип)

Вебзастосунок, який за фото лотка зі свіжою ягодою орієнтовно оцінює якість партії та формує PDF-звіт.
Основна ягода — **ожина**; є експериментальні профілі для лохини, малини й полуниці.
Усе рахується в браузері на пристрої: фото нікуди не надсилаються, сервер не потрібен.

> Це демо. Відсотки — частка **площі ягід, видимих на фото**, а не маси чи кількості.
> Пороги вердикту — **демо-значення, їх треба уточнити з технологом**. Оцінка не є лабораторним висновком.

Документи проєкту: [PLAN.md](PLAN.md) — план по етапах, [PROGRESS.md](PROGRESS.md) — що зроблено і як продовжити,
[DECISIONS.md](DECISIONS.md) — прийняті рішення, [EVALUATION.md](EVALUATION.md) — оцінка якості моделі й кольорового методу,
[DATA_SOURCES.md](DATA_SOURCES.md) — джерела даних, ліцензії, атрибуція.

## Що вміє

- партія з 1–5 фото (камера телефона чи файл), результат усереднюється;
- перевірка якості фото ще до аналізу (темне, засвічене, розмите, замале) і підказки, як знімати;
- категорії (єдині для всього продукту): **якісні, недостиглі, пошкоджені / гнилі, пліснява, домішки / стороннє**
  і окремо **«фон / інше»**, що в 100 % не входить;
- профілі ягід: ожина, лохина, малина, полуниця — перемикач на екрані «Нова партія»;
- **три способи аналізу:** «Кольоровий» (за кольором, без завантажень), «Гібрид» (кольоровий + навчена модель як перевірка)
  і «Модель» (лише навчена модель). Модель завантажується при першому виборі й далі працює офлайн;
  якщо вона недоступна — автоматично застосовується кольоровий метод;
- зона ягід визначається автоматично; її можна уточнити, **обвівши пальцем** потрібну ділянку;
- фото з кольоровим шаром категорій і теплова карта дефектів;
- вердикт: придатна для заморожування після сортування / для переробки / відхилити;
- рівень впевненості та позначка «Потрібна перевірка людиною»;
- **оцінка сортувальника**: людина вводить свої відсотки для тих самих фото — зберігається пара «програма — людина» з різницею;
- PDF-звіт українською, історія партій на пристрої (IndexedDB), експорт усього в ZIP для майбутнього навчання;
- **аналітика:** фільтри за постачальником, ягодою й датою, тренд плісняви й недостиглих, вердикти,
  накопичена похибка «програма — сортувальник» і частка пропущеної плісняви; експорт у Excel (.xlsx), CSV і PDF;
- працює без інтернету після першого відкриття (PWA).

## Як запустити

- **Найпростіше:** двічі клацнути `index.html`. Працює все, крім офлайн-кешу та кнопки «Спробувати на демо-фото»
  (браузер не дає сторінці-файлу читати сусідні файли).
- **Як на сервері:** `node tools/serve.js`, далі відкрити http://localhost:8765.

## Як знімати

- зверху й рівно, щоб ягоди займали майже весь кадр; стіни, підлоги й країв лотка — якнайменше;
- рівне світло, без спалаху; по змозі те саме місце й та сама лампа;
- 2–5 фото на партію: різні лотки або різні місця одного лотка;
- якщо програма неправильно визначила, де ягоди, — кнопка «Уточнити зону» на екрані результату.

## Як це працює: кольоровий метод (v1, без навчання)

1. Фото зменшується до 1024 px по довшій стороні.
2. Баланс білого оцінюється за нейтральними світлими пікселями й обережно виправляється.
3. **Зона ягід.** Біла стіна і біла пліснява мають однаковий колір, тому спершу шукається маса ягід
   (груба сітка, змикання, найбільша зв'язна область). Гладкі ділянки того самого кольору (темний стіл, тінь) відсіюються
   за текстурою, синій лоток — за кольором. Або зону обводить користувач.
4. Кожен піксель зони за HSV відноситься до категорії за правилами профілю ягоди. Яскравість нормується за медіаною
   «тіла ягід», тому результат не залежить від того, скільки стіни потрапило в зону.
5. **Кожна біла пляма розглядається окремо** — пліснява, блик чи фон:

   | Ознака плями | Висновок |
   |---|---|
   | торкається краю зони, межує з лотком чи стіною | поза зоною |
   | дуже мала | блик (рахується як ягода) |
   | більша за 5 % зони або навколо менше половини ягід | фон / інше |
   | дуже яскрава, з різким краєм, невелика | блик |
   | гладка всередині, як папір чи пластик | фон / інше |
   | нерівна всередині, серед ягід | **пліснява** |

6. Рахується частка площі кожної категорії **від площі ягід**, вердикт за порогами та впевненість.

Профілі: **ожина** — темне якісне, червоне й зелене недостигле; **лохина** — синє якісне, сизий природний наліт пліснявою
не вважається (пліснява має бути нейтрально-білою і світлішою); **малина** й **полуниця** — червоне якісне, бліде й зелене
недостигле, чашолистики полуниці — «фон / інше», а не домішка.

Впевненість — це не статистична точність, а сума штрафів: мала зона ягід, темне, пересвічене чи нечітке фото,
багато бліків, багато «сірих» ділянок, багато фону в зоні, сильний відтінок освітлення, експериментальний профіль,
результат біля порога, розбіжність між фото.

### Відомі обмеження кольорового методу

- тонкий сірий наліт плісняви не відрізняється від розсіяного відблиску, тому **відсоток плісняви — нижня оцінка**;
- «м'якість краю» плями на практиці майже не відрізняє плісняву від блика (на зразку різкість краю в обох однакова),
  тому вона враховується лише разом із яскравістю; головні ознаки — оточення ягодами й нерівність усередині;
- **пошкоджені / роздавлені ягоди за кольором не визначаються** — у кольоровому режимі ця категорія завжди 0 %;
- видно лише верхній шар; фото під кутом завищує вагу ближніх ягід;
- темний лоток чи стіл із текстурою (тканина, сітка) може потрапити в зону ожини — тоді зону треба обвести вручну;
- пороги ожини підібрано на одному реальному фото; профілі лохини, малини, полуниці — **експериментальні**:
  кольори підібрано за типовими значеннями й перевірено лише на синтетичних сценах.

## Навчена модель і режими аналізу

| Режим | Що робить | Коли обирати |
|---|---|---|
| **Кольоровий** | лише кольоровий метод вище | завжди працює, нічого не завантажує; ручні налаштування кольорів |
| **Гібрид** | основа — кольоровий метод; модель знімає «плісняву» там, де впевнено бачить фон (стіна, папір), додає плісняву, яку колір пропустив, і (для полуниці) «пошкоджені» | рекомендований режим, коли модель завантажена |
| **Модель** | клас кожного пікселя визначає модель; ручна зона обмежує аналіз | для порівняння й перевірки моделі |

- **Модель:** MobileNetV3-small (torchvision, BSD-3) + легка «голова» FPN, ~1,1 млн параметрів, файл `models/berry-seg.onnx` (3,6 МБ, float32).
  Вихід — клас для кожної клітинки 4×4 px фото, зменшеного до 1024 px, і допоміжний вихід «вид ягоди».
- **У браузері:** ONNX Runtime Web 1.31.1, WebAssembly (`vendor/onnxruntime-1.31.1/`, 14,8 МБ). WebGPU не використовується:
  його збірка (29,5 МБ) більша за ліміт Cloudflare 25 МіБ на файл, а для такої малої моделі WASM вистачає.
- **Офлайн:** рушій і модель завантажуються при першому виборі «Гібрид» чи «Модель» (або кнопкою в «Налаштуваннях») і далі беруться з кешу.
- **Відкат:** якщо модель не завантажилась, сторінку відкрито як файл чи браузер застарий — застосовується кольоровий метод,
  у звіті з'являється позначка про це.
- **Впевненість:** розбіжність кольорового методу й моделі щодо плісняви або невпевнена модель завжди вмикають «Потрібна перевірка людиною».
- Квантизацію до int8 перевірено й відкинуто: вона ламала виявлення плісняви (DECISIONS.md, D18).

Якість моделі й порівняння з кольоровим методом — у [EVALUATION.md](EVALUATION.md). Коротко: на відкритих даних модель
значно краща за кольоровий метод, але на реальних лотках підприємства її не перевірено — **метрики не гарантують якості на ваших лотках**.

### Навчання (Windows, NVIDIA GPU)

```
powershell -ExecutionPolicy Bypass -File trainingsetup_env.ps1      # .venv з PyTorch CUDA (додайте -Cpu, якщо CUDA немає)
.venvScriptspython.exe trainingdownload.py                       # відкриті набори → datasets/raw (≤ 5 ГБ, без реєстрації)
.venvScriptspython.exe trainingprepare.py                        # → datasets/prepared (~15 хв)
.venvScriptspython.exe training	rain.py --name v3                # → runs/v3/best.pt (~30 хв на GTX 1650)
node toolseval_color.js test
.venvScriptspython.exe trainingevaluate.py --run v3              # → runs/v3/eval.md
.venvScriptspython.exe trainingexport_onnx.py --run v3           # → models/berry-seg.onnx (+ .json)
```

Датасети, сирі фото, чекпойнти й проміжні файли лежать у `datasets/`, `runs/`, `.cache/` і **не потрапляють** ні в git, ні в деплой.
Власні фото підприємства — у `data/custom/` (див. [data/custom/README.md](data/custom/README.md)): для них є автопідказка розмітки
кольоровим методом (`node tools/autolabel.js`).

## Розгортання на Cloudflare

Сайт — це статичні файли з кореня репозиторію; збірки немає. Кожен `git push` у гілку `main` автоматично розгортає нову версію.
У деплой не потрапляють код навчання, тести й документи (файл `.assetsignore`), а датасети, чекпойнти й сирі фото
не потрапляють навіть у git (`.gitignore`).

### Оновлення

1. Змініть файли.
2. Підніміть версію **у двох місцях**: `APP_VERSION` у `js/core/defaults.js` і `VERSION` у `sw.js`
   (тест `tests/pwa.test.js` перевіряє, що вони збігаються). Без цього пристрої показуватимуть стару версію з кешу.
3. `git add -A`, `git commit -m "..."`, `git push` — Cloudflare сам розгорне нову версію.
4. На пристроях з'явиться смужка «Доступна нова версія» з кнопкою «Оновити».

### Відкрити на планшеті чи телефоні

1. Відкрийте посилання в Chrome на Android.
2. Меню **⋮ → Додати на головний екран** (або **Встановити додаток**) — з'явиться іконка.
3. Після першого відкриття застосунок працює без інтернету.

### Що буде видно за посиланням

Сайт відкритий для всіх, хто знає посилання, навіть якщо репозиторій приватний. За посиланням доступні файли застосунку
і демо-фото `data/samples/…`. Якщо це небажано, приберіть демо-фото (кнопка демо тоді не працюватиме)
або закрийте сайт через Cloudflare Access. Фото, які знімають користувачі, за посиланням **не** доступні: вони лишаються на пристрої.

                        verdict (вердикт, впевненість), analyzer (режими аналізу)

js/ui/                  app (каркас, нова партія), result (результат, зона, оцінка сортувальника), history, settings

tests/                  тести: node --test tests/
tools/                  analyze.js (кольоровий метод з командного рядка), serve.js (локальний сервер)
training/               конвеєр навчання моделі (Python; у деплой не йде): download, prepare, synth, train, evaluate, export_onnx
js/ml/                  model.js — модель у браузері (ONNX Runtime Web), режими «Гібрид» і «Модель»

## Перевірка

```bash
node --test tests/
```

Тести (потрібен лише Node 18+, без встановлення пакетів): синтетичні сцени (блик, папірець у лотку, біла стіна, білий лоток
між ягодами, гладкий темний стіл, обведена зона), профілі ягід, пороги вердикту, перевірка якості фото, міграція старих записів,
зразок фото (30 контрольних точок, діапазони часток, зона на весь кадр), стійкість до яскравості, відтінку світла, розміру
й повороту, цілісність офлайн-кешу; режими «Гібрид» і «Модель» на штучних ймовірностях (модель не знімає плісняву без
впевненого фону, «пошкоджені» лише для полуниці, підказка виду, розбіжність → перевірка людиною), відкат на кольоровий метод,
розмір файлів для деплою менший за ліміт Cloudflare.

Якість навченої моделі перевіряється окремо, Python-скриптом `training/evaluate.py` (див. [EVALUATION.md](EVALUATION.md)).

Подивитися, що кольоровий метод бачить на фото:

```bash
node tools/analyze.js data/samples/photo_2026-11-12_18-39-37.jpg --out overlay.png
```

Додаткові параметри: `--profile blueberry|raspberry|strawberry`, `--full` (зона — весь кадр), `--mode heat`.

## Формат експорту

ZIP містить `export.json` і `photos/<id>.jpg`. У `export.json` для кожної партії: дані партії, налаштування на момент оцінки
(зокрема профіль ягоди), версія алгоритму, результат по кожному фото (`photos[].summary.percents`, обведена зона `roiPoly`),
зведення (`evaluation`) і оцінка сортувальника (`correction`: частки, вердикт, коментар) або `null`.
Старі записи (до версії 0.2) мають `red` і `green` замість `unripe`.
