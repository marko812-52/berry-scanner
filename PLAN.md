# План розвитку berry-scanner

Кожен етап закінчується робочою версією: тести, перевірка в мобільному розмірі вікна, оновлений README, коміт і push
(push у `main` = автоматичний деплой на Cloudflare). Поточний стан і «що далі» — у [PROGRESS.md](PROGRESS.md),
прийняті рішення — у [DECISIONS.md](DECISIONS.md).

## Етап A. Виправлення кольорового методу (без навчання)

| Крок | Що робимо | Як перевіряємо |
|---|---|---|
| A1 | Єдина таксономія в інтерфейсі: якісні, недостиглі, пошкоджені, пліснява, домішки + «фон / інше» (не входить у 100 %) | тести ядра, міграція старих записів історії |
| A2 | Пліснява лише всередині зони ягід і лише в оточенні ягід; ознаки плями: яскравість, м'якість краю, однорідність; блик = дуже яскраве з різким краєм; велике/гладке біле = «фон / інше» | синтетичні сцени (стіна, білий лоток, папірець у лотку, блики), зразок фото |
| A3 | Ручне уточнення зони обведенням (довільний контур пальцем), а не лише прямокутником | тест растеризації контуру, перевірка в браузері |
| A4 | Профілі ягід: ожина (основний), лохина (білуватий наліт ≠ пліснява), малина, полуниця; перемикач на екрані «Нова партія» | синтетичні сцени на кожен профіль; на реальних фото — після етапу B (відкриті набори) |

**Очікувана якість.** На зразку ожини: стіна й лоток не дають плісняви (вже так), менше хибної плісняви від бліків.
Тонкий сірий наліт і далі не відрізняється від розсіяного відблиску — відсоток плісняви лишається нижньою оцінкою.
Профілі лохини, малини, полуниці підібрано за загальними знаннями про колір і перевірено лише на синтетиці та
відкритих фото — у звіті вони позначені як експериментальні.

**Ризики.** Пороги підібрано на одному реальному фото; інша камера чи лампа можуть їх зсунути
(є ручні налаштування і ручна зона).

## Етап B. Конвеєр навчання власної моделі

| Крок | Що робимо | Результат |
|---|---|---|
| B1 | Таксономія і таблиця відповідності класів (`training/taxonomy.py`) | один файл — одне джерело правди |
| B2 | Збір відкритих наборів без реєстрації (`training/download.py`, ліміт ~5 ГБ, перевірка місця на диску), `DATA_SOURCES.md`; `data/custom/` з автопідказкою розмітки кольоровим методом | `datasets/` (поза git) |
| B3 | Підготовка: усе зводиться до грубих масок класів; розбиття train/val/test за зображеннями-джерелами | `datasets/prepared/` |
| B4 | Навчання легкої сегментаційної мережі (MobileNetV3-small + легка «голова», змішана точність, малий batch), ≤ 1–2 год на експеримент | `runs/…` (поза git) |
| B5 | Оцінка на відкладеній частині: метрики по класах, recall плісняви, хибна пліснява на білих поверхнях, порівняння з кольоровим методом; якісний огляд на `data/samples` | `EVALUATION.md` |
| B6 | Експорт в ONNX + квантизація; у браузері — ONNX Runtime Web (WASM, WebGPU якщо є), ліниве завантаження, кеш для офлайну, відкат на кольоровий метод; режими «Кольоровий / Модель / Гібрид» | `models/*.onnx` (єдине, що йде в деплой) |
| B7 | Автовизначення виду ягоди — лише якщо даних вистачить на чесну перевірку; інакше лишається ручний перемикач | рішення в DECISIONS.md |

**Чому сегментація, а не детекція.** У звіті потрібна частка по категоріях; у лотку ягоди лежать щільною масою,
пліснява й домішки — це плями, а не окремі «об'єкти». Частку за площею сегментація дає напряму й так само,
як кольоровий метод, тож їх можна порівнювати і поєднувати в гібриді.

**Очікувана якість — чесно.** Відкритих наборів саме «лоток свіжої ожини з пліснявою» з піксельною розміткою
немає. Модель вчиться на суміші: відкриті набори (ягоди на кущі, окремі ягоди, полуниця зі сірою гниллю тощо),
синтетичні сцени й автопідказки. Метрики на відкладених відкритих даних **не гарантують** якості на лотках
підприємства. Тому режим за замовчуванням обирається за результатами оцінки, а не наперед; найімовірніше
це буде «Гібрид» (кольоровий метод + модель як фільтр фону й бліків) або «Кольоровий».
Справжній приріст дасть донавчання на 100–300 фото підприємства з виправленнями сортувальника (етап C це готує).

**Ризики.** 4 ГБ відеопам'яті (тому мала мережа й малий batch); різнорідність наборів і ліцензій;
зсув домену «поле → лоток»; розмір файлів ONNX Runtime Web проти ліміту Cloudflare 25 МіБ на файл.

## Етап C. Додаткові функції

| Крок | Що робимо |
|---|---|
| C1 | Режим перевірки: оцінка сортувальника для того ж фото, пари «програма vs людина», різниця, накопичена похибка, окремо частка пропущеної плісняви; експорт для донавчання |
| C2 | Рівень впевненості в звіті й позначка «потрібна перевірка людиною» (є у v0 — доповнити сигналами моделі та розбіжністю «колір vs модель») |
| C3 | Панель аналітики: історія, тренди, фільтри за постачальником і датою, експорт у Excel/CSV і PDF |
| C4 | Партія з 1–5 фото з усередненням; перевірка якості фото до аналізу (засвічене, темне, розмите); підказки по зйомці |

## Порядок і точки розгортання

1. **A** → коміт, push (деплой 1: видимий результат).
2. **C4 + C1 + C3** можна робити, поки качаються дані й іде навчання → коміт, push (деплой 2).
3. **B1–B5** → `EVALUATION.md`, коміт (код і звіти, без даних).
4. **B6** → модель у браузері → коміт, push (деплой 3).
5. **C2**, **B7**, підсумкова перевірка, README → коміт, push (деплой 4).
